## Overview

This lab is about one of the most underappreciated physical attack surfaces in enterprise environments: the USB port. Specifically, I built a rogue HID implant using an RP2040 microcontroller running CircuitPython. When plugged in, it enumerates as a standard USB keyboard - because it *is* one, from the OS's perspective - and then types out a PowerShell reverse shell payload entirely autonomously.

The underlying attack class is BadUSB, documented publicly since Black Hat USA 2014. The core premise hasn't changed: the USB HID class is unconditionally trusted by every major OS. Windows, macOS, Linux - they all have the same assumption baked in: keyboards are safe peripherals. There's no "are you sure you want to let this keyboard type?" prompt. The OS installs the driver, the keyboard reports keys, and that's that.

What makes the RP2040 particularly interesting for this is CircuitPython's adafruit_hid library. You can implement a fully functional USB HID keyboard in maybe 30 lines of Python. No cross-compilation, no toolchain setup. Drag a UF2 file onto the BOOT drive, drop a `code.py` in place, and you have a keystroke injection device. The barrier to replication is basically zero, which is exactly what makes this worth studying from a defensive standpoint.

## Environment

- **Implant:** RP2040 PCB - CircuitPython 8.x, adafruit_hid 6.x library, UF2 drag-and-drop flashing via mass storage bootloader
- **Victim:** ThinkPad P53 - Windows 11 22H2, Windows Defender active and up to date, no USB device policy enforcement configured
- **Monitor:** Wireshark 4.x + USBPcap 1.5.x driver, tapped on the victim's USB host controller before insertion

## Firmware Setup

Flashing CircuitPython is the easiest part. Hold BOOTSEL on the RP2040, plug in USB, and it appears as a mass storage drive called RPI-RP2. Drop the CircuitPython `.uf2` onto it. It reboots into a CIRCUITPY drive with a `code.py` entry point.

Next, copy `adafruit_hid` (the full library bundle folder) into `/lib` on the CIRCUITPY drive.

The `code.py` starts with a deliberate 5-second delay:

```python
import time
import usb_hid
from adafruit_hid.keyboard import Keyboard
from adafruit_hid.keyboard_layout_us import KeyboardLayoutUS
from adafruit_hid.keycode import Keycode

time.sleep(5)

kbd = Keyboard(usb_hid.devices)
layout = KeyboardLayoutUS(kbd)
```

That 5-second delay matters. Windows needs 1–2 seconds to enumerate the device, install the HID class driver, and register the input device with the window manager. If you start injecting keystrokes before the OS is ready, they get dropped. Five seconds is conservative but reliable across different hardware.

## Payload Development

The payload is a PowerShell reverse shell one-liner. Running it raw through keystroke injection creates problems: the PowerShell invocation string contains pipes, dollar signs, backticks, and quotes - all of which can be misinterpreted or dropped depending on the active keyboard layout and timing. The solution is base64 encoding.

The injection sequence is:
1. `WIN+R` to open the Run dialog
2. Type `powershell` and hit Enter
3. Wait 1.5 seconds for the PowerShell window to open
4. Paste the base64-encoded payload string
5. Hit Enter

The payload itself is a standard `$client = New-Object Net.Sockets.TCPClient` reverse shell, encoded to base64 and passed to `powershell -EncodedCommand`. This sidesteps all the quoting and escaping issues.

The keystroke timing was the most empirically interesting part. At 20 ms inter-keystroke delay, I measured approximately 8% character drops - the host HID stack was occasionally too slow to service reports. At 50 ms, drops went to zero. That's the relevant `keyboard.write()` call:

```python
# keyboard.write() injects one char at a time with the layout's default delay
# For longer strings, use layout.write() which handles the full string
layout.write(encoded_payload)
```

The `adafruit_hid` KeyboardLayoutUS uses a configurable inter-key delay that defaults to a safe value, but it's worth tuning explicitly rather than relying on the default.

## USB Capture Setup

Before inserting the implant, I installed the USBPcap driver on the victim machine and opened Wireshark. USBPcap creates a virtual capture interface for each USB host controller. I selected the controller the target port was connected to.

The capture records the full USB enumeration handshake: `GET_DESCRIPTOR` requests (device descriptor, configuration descriptor, HID report descriptor), `SET_ADDRESS`, `SET_CONFIGURATION`, and then the ongoing HID interrupt transfer stream once the device is active. This gives a complete record of what the host saw.

## Implant Insertion & Timing

Plugging in the implant, Windows showed the standard "Installing device driver" notification in the system tray. The HID class driver installed in about 1.2 seconds - no internet lookup required, it's built in. Then the 5-second firmware delay ran, and injection began.

The average plug-to-execution time across 10 trials was **4.2 seconds**: ~1.2 s enumeration + 5 s delay − (delay runs concurrently with driver install for most of it in practice) + ~0.8 s injection + ~0.5 s PowerShell startup. The first shell callback arrived at the ncat listener on TCP 4444 at T+4.2 s.

Listener setup on the attacker side:

```bash
ncat -lvnp 4444
```

## Traffic Analysis

The Wireshark capture showed what I expected: from the protocol perspective, this device is indistinguishable from any commercial USB keyboard.

The HID report descriptor identifies device class 0x03 (HID), subclass 0x01 (boot interface), protocol 0x01 (keyboard). The 8-byte boot protocol report format is identical to every standard keyboard. Windows Device Manager listed it as "USB Input Device" under the Human Interface Devices node with no anomalous attributes - vendor ID was the generic RP2040 VID, but that's not flagged anywhere.

No EDR alert fired during enumeration or during the initial payload injection. Windows Defender sat quiet through the reverse shell callback. It did eventually flag a registry run key persistence modification I added later in the lab - the initial `cmd.exe` process spawned from `powershell.exe`, which was itself spawned from `explorer.exe` via the Run dialog, apparently didn't trip any behavioral rules.

That's the blind window: the injection itself is clean. What you *do* with the shell afterward is where detections start appearing.

## Findings

1. **HID enumeration is indistinguishable from commercial keyboards** - descriptor analysis in Wireshark showed no differentiating fields; no EDR alert on enumeration
2. **4.2 s average plug-to-execution time** - 10-trial average; theoretically reducible to ~2.5 s by cutting the firmware boot delay to 2 s on well-known hardware
3. **Keystroke rate sensitivity confirmed** - 20 ms inter-keystroke delay produced ~8% character drop rate; 50 ms produced 0% drops across all trials
4. **Defender blind window during initial execution** - no alert on reverse shell callback; registry persistence modification flagged within ~30 s of creation

## Lessons Learned

The obvious defensive takeaway is that OS trust in HID class devices is essentially unconditional by default, and that's unlikely to change because it would break every keyboard and mouse in existence.

Practical mitigations:

- **USBGuard (Linux)** - policy-based USB device authorization daemon; can allowlist by device descriptor attributes and block anything unrecognized
- **Windows Group Policy / MDM USB allowlisting** - `USBSTOR` policy can restrict storage class; HID allowlisting requires third-party endpoint tools (e.g., device control modules in CrowdStrike, Carbon Black)
- **Physical port locks** - decidedly low-tech but effective at the access layer; not much help against an insider
- **Disable AutoRun/AutoPlay** - not directly relevant here (HID, not storage) but good hygiene
- **Behavioral detection on `powershell.exe` spawned from `explorer.exe`** - the Run dialog injection pattern is detectable; most mature EDRs have this rule but it depends on policy configuration

The 4.2 s window means that an attacker needs approximately 5 seconds of unattended physical access to an unlocked workstation. That's a meaningful constraint in some environments and completely negligible in others.
